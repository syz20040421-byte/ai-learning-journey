# 学习笔记
1. FastAPI 装饰器与路由
- @app.get("/") 将函数绑定到 GET 请求的根路径，返回字典自动转 JSON。
- 路径参数：用 {name} 占位，函数参数名需一致，如 def get_student(name: str)。
- 查询参数：用 Query(default, ge=, le=) 定义默认值和校验范围，自动处理 422 错误。
- 状态码：@app.post(..., status_code=201) 写在装饰器上，表示创建成功返回 201。
- 路由顺序：固定路径（如 /students/stats）必须放在动态路径（如 /students/{name}）之前，否则会被动态路径捕获。
- 将状态码写在 return 里（无效），应写在装饰器 status_code=。
- 路径参数名与占位符不一致会导致匹配失败。
2. Pydantic 模型与请求体验证

- 定义模型：class Student(BaseModel): name: str; age: int; score: float = Field(ge=0, le=100)
- 自动校验：FastAPI 自动校验请求体，失败返回 422，无需 try/except。
- 模型转字典：Pydantic v2 用 .model_dump()，旧版用 .dict()。
- 不要混用 .dict() 和 .model_dump()（版本不匹配）。

3. httpx 发起 HTTP 请求
- 基本用法：httpx.get(url, params=..., timeout=10)，必须设置超时避免卡死。
- 状态码与成功判断：
- resp.status_code 直接获取。
- resp.is_success 仅在 2xx 时为 True（注意不是 resp.ok）。
- 响应头获取：resp.headers.get("Content-Type") 安全获取，避免 KeyError。
- 查询参数：params 字典自动拼接到 URL 后面。
- JSON 解析：resp.json() 返回字典。
- httpbingo 特点：args 字段的值是数组（如 {"name": ["alice"]}），取用需带 [0]。
- URL 缺少协议（如 httpbingo.org/...），应写 https://httpbingo.org/...。
- 不要混淆 requests 的 resp.ok 与 httpx 的 resp.is_success。
- 未设置 timeout=10，可能导致请求卡死。
4. Python 基础与编程习惯
- 字典安全取值：s.get('score', 0) 在键不存在时返回默认值，避免 KeyError。
- 生成器表达式 + next()：next((s for s in list if cond), None) 查找第一个匹配项，找不到返回默认值。
- 列表推导式：[s for s in STUDENTS if s.get('score', 0) >= min_score] 一行过滤。
- 异常抛出：raise HTTPException(status_code=404, detail="not found")，FastAPI 自动转为 JSON 响应。
- 关键字段（如 name）用 .get() 而不用直接索引，可能掩盖数据错误。
5. 命令行与项目环境
- uvicorn 启动命令：python -m uvicorn 模块路径:app --reload。
- 模块路径写法：用点号替换目录分隔符，不写 .py 后缀。
- 虚拟环境激活：使用 Activate.ps1 或 source，激活后终端前缀显示 (venv)。
- 将 -m 当作独立命令直接运行（-m uvicorn ... 不合法），正确应是 python -m uvicorn ...


# 今日三问
1. **（昨天代码追问）** Day 14 你写的 `safe_score` 里 try/except 捕获 ValidationError 返回 `(None, 错误信息)`，而 `make_student` 故意不捕获让它抛出去。今天 FastAPI 的 POST 路由你一行 try/except 都没写，坏数据却自动返回 422——「谁负责捕获异常」这件事，三种做法（你捕获/不捕获/框架捕获）各自适合什么场景？为什么 FastAPI 选择了「框架捕获」而不是「让你在函数里捕获」？
- FastAPI的参数校验失败自动返回422本质上是框架在路由层捕获了Pydantic抛出的ValidationError，这对应了“框架捕获”的做法。
- 我捕获：适合需要对特定校验错误做定制化响应（比如错误信息要翻译成多语言、需要聚合多个字段错误、或者要把校验失败额外记录到监控系统），或者校验逻辑不在Pydantic模型内（例如需要检查数据库中是否已存在某条记录），这时会手动抛出HTTPException并捕获它；
- 不捕获：适合使用了全局异常处理器（如 @app.exception_handler），希望在统一的地方集中处理所有异常，让业务函数保持干净；
- 框架捕获：这是FastAPI的默认行为，适合标准化、通用的格式校验错误（字段缺失、类型错误、数值越界），这些错误不需要每个接口特殊处理。
- 原因：本质上是将“参数格式校验”与“业务逻辑”分离：业务函数只关心“数据合法后做什么”，而校验（字段缺失、类型错误、范围越界）作为基础设施层的职责，由框架在请求进入函数之前统一处理并自动返回422，这样既减少了大量重复的样板代码，又保证了所有接口的错误响应格式统一、与 OpenAPI 文档一致，同时如果你需要定制错误格式，也可以通过全局异常处理器一次性覆盖，而不需要修改每个接口函数
2. **（今日机制）** `GET /students?min_score=abc` 返回的是 422 而不是 500。422（客户端数据不合法）和 500（服务器崩了）对**调用方**（比如明天的你、下周的手机前端）来说，处理方式有什么本质不同？为什么 FastAPI 特意区分这两者而不是一律报 400 或 500？
- 收到 500（Internal Server Error）：意味着“服务器内部出问题了”。调用方没有任何办法通过修改请求参数来让它成功
- 收到 422（Unprocessable Entity）：意味着“你给我的数据不合规”。调用方明确知道问题出在自己发来的参数上，应当：立即修正输入
- 不用 500 避免把客户端的错误栽赃给服务器，防止前端误报警和无效重试；不用 400 是因为 400 太笼统（只代表语法错误），而 422 更精确地表示“参数合法但不合规”（如类型错、范围越界），便于前端精准提示用户；更重要的意义是让调用方一眼判断“该改前端代码/用户输入”还是“该找后端运维”，通过状态码明确责任边界。
3. **（场景题）** 你的 `GET /students/{name}` 用路径参数接收名字。如果用户传的名字是中文「张三」（URL 编码后是 `%E5%BC%A0%E4%B8%89`）或带空格的名字，路径参数还能正常工作吗？什么类型的数据**不适合**放路径参数（提示：想想要是按分数区间查 `GET /students/70~100` 会怎样）？
- 中文和空格都能正常工作——浏览器会自动 URL 编码，FastAPI 收到后自动解码，你的函数直接拿到原始字符串（如 "张三" 或 "John Doe"），无需手动处理。
- 不适合放路径参数的是“过滤条件”和“非唯一标识符”，比如 GET /students/70~100——路径参数应放身份标识（ID/唯一名称）用于定位单一资源，而筛选条件（如分数区间、排序）应用查询参数（?min_score=70&max_score=100），否则路由会混乱。
