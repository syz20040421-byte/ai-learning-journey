# 笔记
1. 推导式：实现 `squares_of_evens`、`word_lengths` 和 `unique_chars` 时，体验了将“建容器、循环、添加”压缩成一行的效率。列表、字典、集合推导式分别用 `[]`、`{}`、`{}` 生成对应结构，代码更简洁且执行更快。同时注意可读性，每个推导式只用一个 `for` 和一个 `if`，避免嵌套过深。

2. 生成器：`first_n_squares` 用 `yield` 实现惰性求值，调用返回生成器对象，`iter(gen) is gen` 验证其特性。`sum_squares_upto` 用生成器表达式 `sum(i*i for i in range(n))` 不存储中间结果，内存友好。关键区别：生成器只能单次遍历，无 `len()` 和下标；需重复访问或计算长度时必须用列表。

3. `pathlib`修复路径：硬编码 `"submissions/2026-08-10/cities.csv"` 在归档后失效，改用 `Path(__file__).resolve().parent` 获取脚本所在目录，再 `/` 拼接文件名。这样脚本挪到任何目录都能正确找到数据文件，解决了昨天的 FileNotFoundError 回归 bug。

4. Git分支与冲突：创建分支修改路径，切回 `main` 同一行故意改写，合并时产生冲突。文件内标记 `<<<<<<<`、`=======`、`>>>>>>>` 分别表示当前、分隔线、被合并分支的改动。手动删除标记保留正确版本，`add` 并 `commit` 完成解决。切分支前需确保工作区干净。

5. 工程习惯：删除主流程中包裹 `fetch_weather` 的无用 `try/except`，因内层已吞掉所有异常，外层永远不触发。结合 pathlib 和 Git 规范提交，好的代码不只运行正确，更应路径灵活、异常处理真实、历史可追溯，这些“地基”虽看不见，却决定后续功能的稳定性。
# 每日一问
1. **（昨天代码追问）** 你主流程那层 `try/except requests.RequestException` 包着 `fetch_weather(...)`，但 `fetch_weather` 内部自己 except 完、只返回 None，**永不抛异常**。那这层 try/except 到底接得住什么？删掉它重跑，程序行为有变化吗？（先动手删了再答——编码任务 a 已经让你删了，用实跑结果说话）
- 什么也接不住
- 整体没有变化
- RequestException 是requests模块中大多数网络请求异常的基类，主流程的try中不可能发生网络请求方面的异常，因为网络请求异常在`fetch_weather(...)`已经被接完了，所以主流程中的`try...except...`永远不会触发
2. **（今日机制）** 列表推导式 `[x*x for x in range(1000000)]` 和生成器表达式 `(x*x for x in range(1000000))` 都能迭代，为什么内存差几十 MB？什么场景**必须**用列表推导式而不能用生成器？（提示：想三个词——len()、下标、遍历两遍）
- 因为列表推导式会将所有结果计算出来并储存，而生成器表达式只返回一个生成器状态，并不存储任何数据
- 只需单次顺序遍历时用生成器省内存，但凡涉及重复迭代、下标访问或长度计算，则必须用列表推导式。
3. **（场景题）** 你和同学各改了一个文件的不同行，git merge 会不会冲突？如果改的是**同一行**呢？冲突标记 `<<<<<<<` / `=======` / `>>>>>>>` 分别代表哪边的代码？你怎么决定最终留哪版？
- 改不同文件或不同行时，Git 能自动合并，不会产生冲突。
- 若修改了完全相同的行，Git 无法判断，必然会产生冲突。
- 冲突标记中，<<<<<<< HEAD 到 ======= 是你的代码，======= 到 >>>>>>> 是对方的代码。
- 解决方式：沟通确认业务逻辑，删掉所有标记并保留正确代码，最后 git add 和 git commit 完成合并。
